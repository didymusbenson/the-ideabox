# 03 — Simulation, implementation and persistence requirements

The catalog defines content; this document is the state transition contract. Implement mechanics as pure domain operations, independent of rendering, to make the online and offline economy testable. Values are from [the v1 catalog](../../data/progression-v1.json) unless an engine-only limit is stated here. [Storage requirements](06-storage.md) define the shared hard item cap and overflow rules in addition to local cycle buffers.

## Architecture and compatibility

**ENG-01:** Web-first TypeScript, React + Vite for UI and PWA shell, pure TypeScript domain/simulator modules with no DOM, storage or framework dependencies. Use a content loader/validator that converts the committed catalog into typed definitions at startup; reject malformed data, never silently substitute an unrelated resource. Keep dependency graph, accounting, clock, power, combat, save migration and UI components separate. React views dispatch intents and subscribe to state selectors; UI cannot mutate stocks or timers directly. No server required, no third-party persistent trackers, no sign-in.

Suggested clean structure (actual project creation is a later implementation task):

```
src/domain/{catalog,world,actions,inventory,recipes,progression,simulation,power,combat,prestige}
src/persistence/{schema,store,migrations,import-export,lease}
src/ui/{shell,orchard,workshop,farm,quarry,arena,factory,grid,inventory,goals,settings}
src/pwa/{offline-assets,update}
tests/{unit,integration,property,e2e}
```

Use strict TypeScript, deterministic unit tests with fake clock/RNG, browser integration tests, mobile viewport and touch/keyboard test coverage. Deploy static assets independently of content. Bundle catalog/art/icons/fonts needed for core play; after first successful load, offline launch and all non-network gameplay must work. If service worker unavailable, ordinary online browser gameplay still works; show honest offline status, not forced install. Test current Safari iOS/iPadOS, Chrome Android, desktop Chrome/Firefox/Safari; minimum support based on actual feature checks, not user-agent assumptions.

**ENG-02:** No app build in this requirements commit. URLs, identifiers and filenames in the table are stable. Use initial technical implementations with reversible constraints, not permanent hidden limitations; performance target defined below.

## State model (serializable, versioned)

Use integer item counts (safe integers), integer milliseconds (safe integers), integer watts and watt-milliseconds for electricity. All numeric quantities `0..Number.MAX_SAFE_INTEGER`; overflow blocks producing/consuming transition with explicit capacity state, never silently wraps/NaN/Infinity. If v2 needs larger values, migrate to a specified decimal/big-int string representation. Avoid storing derived values (rates, percentages, available stock) as authoritative state.

| Entity | Required persisted fields |
|---|---|
| Profile | schemaVersion, balanceVersion, profileId, settings, earnedPrestige, spentPrestige, perkLevels keyed by stable ID, history (last 20 summaries), lifetime totals/records, current worldId |
| World | unique worldId, startUtcMs, progressionMode (full or root_trial), wonAtUtcMs/null, prestigeAwarded boolean, rng state nonzero uint32, elapsedSimMs, lastSavedUtcMs, lastProcessedUtcMs, online/offline elapsed counters, resource ledger, technology set, cultivar set, milestones, seedAwarded, starterHarvests, clayAutoCollected, totalWorldseedProduced, completedBuildCounts, zone unlocks, all task entities, Arena counters, Grid state |
| Inventory | per-resource onHand nonnegative integer, globally reserved units derivable from job reservations, storage module count by tier, optional target/minimum and overflow policy by resource, automatically produced/delivered resource flags, historical produced/consumed/discarded totals per resource |
| Plot | stable instance ID, cultivar ID or null, remainingMs, ready queue of exact completed bundles, soil selection, tool selection, fractional yield remainder map, collector attachment ID/null, twerker attachment ID/null, enabled, storageUpgradeLevel |
| Field/pen/quarry slot | instance ID, task ID or null, remainingMs, optional current reservation, ready queue, selected tool for Quarry, automation attachment ID, enabled, storageUpgradeLevel, priority |
| Machine | instance ID, station type, selected task ID/null, enabled, queue of {recipeId, count<=99}, repeat flag, output target, input reservation, remainingMs, ready output bundle/null, priority, speed/efficiency upgrade booleans |
| Attachment | instance ID, type, target instance ID/null, configured enabled; detach preserves assignment state but not any lost elapsed timer (see task switch) |
| Generator | instance ID/type, enabled, selected fuel ID, fuelRemainingMs, priority, configured enabled |
| Power | per-battery charge integer watt-ms, max battery charge (600,000 watt-ms each), priority per powered job, optional fuel keep-minimum; demand/supply are derived |
| Arena | selected unlocked enemy, HP/maxHP, current attempt/reserved ration/result roll (only set when resolved), remainingMs, opponent-specific wins/lossStreak/firstWinClaimed, global consecutiveAutoLosses, auto enabled, cooldownMs, auto-decision status |
| Grinder | machine-like instance, assigned mastered enemy, ration reservation, remainingMs, power requirement, output target, enabled |
| Save envelope | version, balanceVersion, revision, timestamp, checksum, profile+world payload, installation-specific writer ID; checksum detects corruption, not anti-tamper |

State validated at load/action boundary: IDs known and unique; max ranges valid; inventory/health/energy nonnegative; reservation item amounts valid; no reservation on nonexistent job; unlocked tech dependencies satisfied; exactly one world; effects present for unlocked tech; no duplicate attachment assignment; only unlocked recipes/known cultivars assigned; completion facts not repeatable. A saved state may contain older schema/balance versions only via explicit migration. Avoid rerandomizing outcomes or generating free resources by reload, switch or stale writer.

## Inventory and construction

**INV-01:** Shared resource ledger, visible from every tab as available amount and reserved amount. Shared warehouse capacity = 160 + built module capacities; used = sum(onHand) + sum(reserved input units), including Worldseed and seed. Materials in manual/local buffers and a machine's single pending finished bundle are not inventory until collected or transferred by automation. This is a gameplay cap below the numeric safe-integer limit. See [ST-01..ST-04](06-storage.md). `onHand` is spendable stock including safety reserve (manual user may explicitly spend it), excluding reserved inputs; reserve is not a second inventory count. Automated scheduling may spend only stock above configured minimum; manual purchases/crafts may spend below by explicit action. Recipe outputs and by-products credit only once at completion. Source/usage detail for every catalog ID; no unlisted resource can appear.

**INV-02:** Unlock purchase is atomic (all tech requirements true AND enough stock AND not already owned); debit entire bundle and apply effect in same transaction. Zone/machine/field/generator initial slots and storage modules are created only by first purchase of its technology, with one each for every slot-bearing effect. E.g. `biofuel_line` creates one fermenter and one biofuel generator; `grid` one combustion; `advanced_grid` one advanced unit. `factory` grants one processor. `field`, `animal_pen`, `iron_pick` each grant one respective producer. `arena` opens one encounter slot and does not create a grinder. Storage tech creates its first module and increases shared capacity atomically with material debit; repeat module construction adds one module, maximum four per tier; module effects never occupy stock or depend on power. No duplicate grants if a button is double-tapped or reload occurs. A technology may be known yet no resource currently in stock; don't confuse knowledge with material balance.

**INV-03:** Builds are atomic paid actions; check prerequisite, target capacity, additional build count cap and global cap before debit. Plot price uses current plot count p, candidate formula in catalog. Initial plot and prestige bonus count toward 64 plot maximum; additional plots cannot be sold in v1. Every other build cost is flat until cap; max fields 32, pens 16, Quarry slots 32, each initial machine type 16 total slots, each generator type 32 total (additional builds exclude free first). Retain attachments when detached; no automatic destruction/sale. Local buffer kit targets one plot/field/pen/quarry/ordinary machine, three additional completed cycle capacity (max 12), cannot exceed three per target. Batteries max 16; charge storage grows by stated capacity, never fills for free. Speed and efficiency kits one of each on powered machine only, cap before purchase. Attachments cannot outnumber target-type maximum and one per compatible slot/type; clockwork and powered twerker mutually exclusive on a plot. Quarry drill and deep drill mutually exclusive: technology unlocks ability to choose deep-drill mode on an existing drill (per slot, upgrade consumes its listed one-time unlock cost, then compatible drill instance may opt into deep mode); the first ordinary quarry drill still needs per-slot build. Alternatively switch back to standard at no cost. The deep-drill tech grants the upgrade design, not a free producer. Field, pen and Quarry attachments respectively require matching slot. Grinder count max16 and only after one enemy mastered. Assignment is mutable after safe cancellation and cannot create an output.

**INV-04:** Bench recipes of duration zero are atomic one-shot, input debit and output credit in one transaction. User selects qty 1..99, operation succeeds only for full amount requested (offer max affordable). No free instant recipe with zero input. Repeating instant recipes after router are **demand-only**, never uncontrolled loops: a configured target replenishes at most missing amount rounded to batches; limit 99 per scheduler boundary, re-evaluate after later timestamp or next consuming event. No arbitrary attempt count per render. A powered timed batch reserves inputs on start, does not consume other jobs' reserved stock, then converts reservation to outputs. Manual timed tasks and Arena ration follow same reservation model. Cancel before completion releases ordinary job reserve and discards progress (Arena ration is consumed at start; see Arena). Recipe switch cancels only when confirmed if progress/reserve/buffer would be affected, never deletes finished output; either require collection of ready buffer or transfer it first with capacity check. Queue items not started never reserve resources. On settings change, if enabled and output full, block before reservation; a new manually started timed job may reserve its ordinary inputs at full warehouse if no output is held; automated repeating jobs wait if the current projected net output cannot fit (but a previously started job can complete into a held bundle if stock changed). At completion consume reserved inputs exactly once, then check hard capacity against actual remaining stock plus output; if overflow, hold completed output in one ready bundle and do not start next batch until it can enter ledger. Never refund finished batch inputs. Count completed output only on successful delivery (e.g. Worldseed completion). Instant bench crafts check net occupancy atomically; at full warehouse allow net reducing/nonincreasing recipes and storage construction. Manual unreserved disposal requires explicit confirm; automatic trim only opt-in per resource after router; protect seed/Worldseed. See storage requirements. 

## Timing and deterministic simulation

**SIM-01:** All tasks simulated from timestamps and work remaining, not animation frames or browser `setInterval` frequency. In foreground use performance.now delta while mounted, and a wall-clock UTC stamp only for persistence/return. On startup/resume, derive elapsed = clamp(nowUtcMs - lastProcessedUtcMs, 0, 43,200,000). Set lastProcessedUtcMs to the actual observed max(previous,now) once elapsed reconciled; capped extra time is discarded, not claimable on reload. Clock reversal grants no elapsed, no negative work. No tapping/offline manual interaction events are synthesized. Record used/suppressed elapsed for summary. Active runtime continuously advances using monotonic time; on visibility change flush then release foreground loop, recompute return elapsed from last processed stamp. Avoid double-counting with concurrent timers.

**SIM-02:** Process events at exact next boundary: completions, buffer transitions, changes in power availability/fuel, recharge/cooldown, known player intents. Model milliseconds and round configured fractional effective duration up to nearest ms (minimum 250ms timed job). Compute fixed cycle work at **start of cycle** using applicable base modifiers; during a cycle, attachment/upgrade toggles affect subsequent intervals but changing speed/soil/tool choice applies next cycle (no instant progress exploit). Base work = catalog seconds ×1000 × soil duration factor (Orchard) × starter prestige factor (starter only) × speed kit (powered station). Attachment and power affect progress rate separately, not work: clockwork rate = 1/0.8 without power; powered auto-twerker rate = 1/0.6 while allocated; Quarry drill/deep mode rates = 1/0.75 or 1/0.5 while allocated. If denied, fall back to ordinary growth/mining rate; no attachment factor is applied twice. Do not double apply soil/tool kit across incompatible task types. Use fixed rational math or integer remainder counters, so splitting elapsed into intervals gives same result. Define active input as subtracting 250 ms of baseline work from selected eligible current timer, never more than outstanding work. No tap through empty/full/ineligible/paused state; one global rolling one-second window (at most 8 accepted inputs, including pointer/keyboard). Tap at exact completion resolves existing completion first, then new eligible cycle if started; never yields duplicate rewards. Active boost cannot bypass power, inventory, queued prerequisites, defeat, or buffer cap. An accessibility hold-to-hasten can dispatch four accepted input intents/sec under the same cap; no user preference requires frantic tapping.

**SIM-03:** Tick scheduler deterministic ordering at a single timestamp: (a) settle all completions from prior interval in stable entity-ID order, including fuel expiry and reserved output; (b) update milestones, health/cooldown and inventory; (c) apply queued player intents ordered by monotonic sequence; (d) retry previously held warehouse deliveries after material-spending/capacity changes (priority then stable ID, oldest whole bundle per producer), resolve demand-limited instant recipes and start eligible next batches in priority then stable ID order, rechecking stock after each reservation; (e) determine next interval's power allocation and eligible progress; (f) advance by the next minimum event delta, not beyond requested elapsed. If an ordinary job has power denied, it holds reservation and remaining time, no further fuel from it. Optional optimized batched simulation must equal exact event processing in golden fixtures. Safeguard against no-progress loops (return diagnostic/block and preserve state, not grant fiction). Stop idle when no task has a future event except known offline cutoff. At equal events, inventory credits precede new reservations; both online and offline share ordering.

**SIM-04:** Buffered Orchard/Farm/Quarry cycles repeat naturally with selected task: outputs enter local ready queue until capacity (default 3); full producer pauses without losing output or reducing timer. Input-bearing pen slot reserves feed before starting. Manual "collect all" transfers oldest complete ready bundles that fit, sequential atomic ledger credit per bundle; leave the next intact if it exceeds shared capacity. Powered collector tries same transfer at completion/available space while allocated, mechanical collector does so without Grid. Network Hold/trim policies apply only to automated transfers and follow [ST-04](06-storage.md). If automatic collection unavailable because power denied, the underlying manual field/quarry/pen continues at base rate until its manual buffer is full; a denied Quarry drill also loses acceleration. Once power returns, drain ready bundles respecting stock cap, then resume automatic progress. Generator output alone does not free a blocked buffer unless attachment is enabled and given allocation. Auto-twerker and collector are independent, can both be attached; powered speed may coexist with mechanical collection. Plot switch resets current incomplete cycle after preview/confirmation, returns ordinary reserved input if any; preserve and collect ready bundles first. Initial Starter field seed awarded on first successful pre-cap first-two chance or guaranteed 3rd starter completion; credit in actual resulting bundle, persist seed flag/counter immediately. Do not roll for a full buffer or on UI rerender. Field seed cannot be consumed by any other recipe.

**SIM-05:** Yield: apply chosen Orchard/Quarry tool multiplier only to base outputs using per-instance per-resource fractional remainders; do not multiply unique seed or combat first-win bonuses. Farm base yields unchanged; soil affects Orchard duration only. For an integer output x and rational multiplier m, output floor(x*m + prior remainder), carry fractional remainder. Remainder belongs to instance + resource and persists through time/save, not credited on cancel; cannot transfer another resource's fractional remainder. Mechanical collectors do not multiply output; powered smelting's better conversion is defined by its distinct recipe. Speed and efficiency kit modifiers change watts/duration only, watts ceil(baseW × speed-power × efficiency-power), never negative, minimum 1 for powered; battery uses integer rate integration. Example speed + efficiency on 8 W machine: ceil(8×1.5×0.75)=9 W, duration 75% original. Changing selected upgrades applies next batch except safety allocation toggles. Tool/soil technologies grant selectable per-slot loadout (not paid per instance); selecting one is free and exclusive with other tiers.

## Power and fuel

**PWR-01:** One global bus. Capabilities requiring Grid: powered auto-twerker 3 W, field harvester 3 W, pen feeder 4 W, Quarry drill 6 W/deep 10 W, automated Arena 6 W, grinder and Factory task wattage as listed. Mechanical collector and clockwork/hand tasks cost zero. Enabled and ready powered task demands rated watts only while it would advance (not full buffer, no input, cooldown, stopped). Generator rates: combustion 20 W, biofuel 45 W, advanced 100 W. Fuel choices explicit per generator; enabled generator burns no unit if there is no runnable powered demand and all batteries full/no charging request. If serving demand/charging it reserves one unit by debiting at burn start, persists remaining burn time; no replacement unit until that duration consumed. It may suspend burn when no demand and storage full; remaining fuel resumes, cannot be refunded or changed mid-burn except disable pauses. Switching selected fuel applies next burn. No fuel allocation if below automated safety reserve; manual refill may override minimum. Energy generated unused and beyond battery capacity is discarded in abstract model. No fuel or power created from nothing at unlock or restart.

**PWR-02:** At each boundary determine runnable load sorted by player priority (1 highest, 5 lowest, default 3), then stable ID. Determine enabled fueled supply plus battery energy. Admit full loads in order within current generator capacity; battery may cover remaining full-load deficits until charge reaches zero (calculate next exact depletion timestamp). If insufficient without battery, skip task for interval rather than partial progress, continue checking lower tasks that fit; indicate "waiting for power". If generators have available fuel, start enough in stable priority/ID order to service desired loads/charge; keep running while useful, pause as above. Batteries charge surplus at available watt rate limited by remaining capacity, discharge deficit up to stored watt-ms; v1 no maximum charge/discharge rate apart from capacity/remaining energy. Process boundaries at fuel exhaustion or battery full/empty; no negative energy or duplicated fuel. UI shows desired and allocated W separately. Example: supply20 W, desired12+10 W, stored20,000 watt-ms, battery bridges 2W for10s; then 12W runs and lower priority 10W waits, battery0. Re-enable source resumes exact progress.

**PWR-03:** A fully depleted world can bootstrap with manual Starter → manual charcoal if needed → manual fuel feed → combustion. Every producer of mandatory first-fuel has a power-free route, even if all machine tasks paused. Routing reserves generator fuel explicitly so broad repeat recipes don't consume it all; if user intentionally spends safety stock, provide a clear blocked Grid recovery link. No involuntary loss of inventory, upgrade or progression on outage.

## Arena and RNG

**ARE-01:** One live encounter at a time. Enemy catalog supplies base chance/duration/damage and guaranteed win reward. Enemy tiers unlock via tech. Maximum HP increases at armor/trial purchases to 130/160/200; heal to new maximum at purchase once. Current HP starts100. Starting a fight requires enemy unlocked, not in cooldown, food >=1, HP>0, no current fight, and full power if automatic. Consume one ration at start, heal 40 up to max, then timer. Manual fight no power. Active tap does not accelerate fights; no RPG stat triangle/equipment combinatorics. Player chooses opponent, first victory always normal guaranteed output plus first-win bonus once; complete win check uses serialized RNG only at event boundary. On loss no reward. Track per-enemy consecutive losses, force the third valid completed attempt to win after two losses; loss streak resets on win. Record RNG even forced outcome consistently: advance once per completed fight and once for each eligible first-two starter seed trial, no extra rolls for forced guarantee. Use xorshift32 (mask uint32 after XOR shifts 13, 17 logical right, 5 left; seed nonzero), number in [0,1) = unsigned state/2^32. Explicit import requires nonzero valid state. No server or secrets.

**ARE-02:** On resolution apply catalog damage (win/loss), then if HP hits 0 enter 60s cooldown (reward of a victorious fight still delivered exactly once, no negative HP). During fight no passive HP regen; when idle and not in death cooldown recover 2 HP/s up to max; fractional ms retained. Cooldown end fully restores HP. Cancel after start consumes food, discards progress, does not award or increment pity/mastery. No items lost on death. Auto battle unlocked by Ward motor; auto starts only if HP at least ceil(maxHP×0.6), ration and power available. Pause on cooldown, insufficient food/HP or power; resume once recovered except **two consecutive automatic losses** pause until player explicitly resumes. Global auto loss count reset on success or manual resume; enemy's pity streak remains, so a third manual/auto attempt can succeed. The UI shows both pause reason and expected damage. 

**ARE-03:** Five completed wins for each enemy unlock mastery for that enemy. A mob grinder purchase requires at least any mastered enemy, and assigning a specific enemy requires that enemy mastered. Grinder consumes one ration at start (ordinary reservation semantics, no live HP), catalog time/watts, deterministic normal drop bundle only; cannot count as kills, first wins or repeat progression rewards. Multiple grinders may run for different or same mastered enemies, subject to cap/power. Grinder can stop/wait and recover like Factory machine; no combat RNG on offline grinder. Auto-battle itself obeys same offline event and loss rules, including power, ration and HP; offline is not unconditional wins.

## Milestone events and stats

**GOAL-01:** Every successful committed transition records relevant event facts in a monotonic world set (deduplicated by event key, not unbounded event log), and updates counters. Evaluate the catalog's event/tech/counter predicates after commit including offline; achievement state never reverts if stock later spent. `harvest:<cultivar/task>` at valid completed buffered or auto harvest; `craft:<task>` upon committed delivery; `produce:<resource>` upon positive material credit; `build:<id>` at successful paid build; `arena:win:<id>` at resolved successful encounter; `buffer:full` when reaches cap, `buffer:resumed` when formerly full becomes runnable; `grid:fuel_started` at fuel debit, `grid:task_resumed` only after previous power block and subsequent allocation; `machine:repeat_completed` on a delivered automatically started timed repeat; `machine:automated_input_completed` when a delivered powered batch has any ingredient ID recorded as produced/delivered automatically earlier in that world (historical prerequisite, no precise lot provenance); `grinder:first_complete` on first delivered grinder output. Record `storage:full` once when warehouse reaches hard cap or a pending output is blocked by insufficient free units; record `storage:resumed` when a previously storage-blocked delivery succeeds. Counters `wins:<enemy>`, `clayAutoCollected`, `worldseedProduced` correspond to persisted world totals, not inventory. The clay counter counts delivered collector outputs from clay cultivar after first collector installed, never manual collection, and counts each delivered unit exactly once; Worldseed counter counts delivered press output exactly once. A milestone is achieved by a fact/counter, never a manually claimable repeat reward.

## Offline, save and updates

**SAVE-01:** v1 localStorage snapshot (small structured JSON) with one live snapshot and two rotating backup slots plus commit pointer. Validate envelope and checksum before committing; write candidate to inactive slot, re-read, validate, atomically switch pointer, retain last good snapshot. Serialization is deterministic (stable keys, no nonfinite values, item counts integer). Use CRC32 over canonical JSON payload (object keys sorted recursively; array order preserved; UTF-8 encoding), with checksum stored outside payload; this detects accidental corruption, not tampering. Use a monotonically increasing revision and worldId; update processed timestamp with state, not separately. On load validate current, fall back to most recent valid backup, offer explicit recovery choice if current corrupt. Never replace an unknown newer version with a blank world. If unable to persist, keep current in-memory state, show blocking data warning and enable export; do not claim saved. Use small snapshot; future IndexedDB migration explicit if browser storage limits require it.

**SAVE-02:** Save after material/tech/build/assignment/queue/completion/decision/setting mutations (coalesce simultaneous transitions into transaction), at least every15s during activity and on page hide/visibility change best-effort. Offline catch-up completes atomically from last checkpoint; persist new state before reporting/claiming catch-up, idempotent if reload mid-reconciliation. A capped/negative-clock interval never re-awarded. Save before intentional reload/application update. Service worker updates prompt at safe checkpoint; no auto-refresh during active catch-up. Persist selected tab, settings (reduced motion/sound/number formatting), per-world balances and UI preferences; no account or external sync.

**SAVE-03:** Prevent two tabs earning from the same world. Use browser Web Locks for a single writer where available plus BroadcastChannel; fallback localStorage lease with random writer ID, revision and expiry (heartbeat while focused, renew at 4s, expire after 12s); only one writer advances/saves, other is read-only and offers "take over" after first releases/lease expires. Recheck owner and revision before every commit; on conflict stop simulation, preserve valid highest revision and prompt reload/restore rather than merge economy. Because fallback isn't truly transactional, keep write candidate checks, refuse concurrent write, test racing tabs. Offline mode does not bypass lease. If a browser lacks local persistence, play can continue with explicit unsaved indicator/export.

**SAVE-04:** Settings export JSON save envelope as download. Import checks <=5 MiB, parsed JSON (never run code), schema version, checksum, resource/tech/owner/ID validation, amounts, reservations, complete preflight before replacing current state. Show source profile/world/time and consequences; require confirmation, back up existing world; unsupported future schema tells user to update, invalid/truncated/oversized leaves current unchanged. Full reset separate confirm and export option. New world after victory uses a single atomic operation: check won/not already transitioned, spend selected points, archive summary and reset only listed world data, save revision and new ID. No prestige reward duplication on reload/import; export is local backup, not competitive anti-cheat. 

**SAVE-05:** Balance changes are keyed separately from schema. v1 saves contain balanceVersion, immutable rule IDs; on updated content define explicit migration and timer policy (preserve completion fraction on changed duration, never create extra outputs; known deprecated IDs mapped or preserved until migration). Do not mutate old saves until validated and migration succeeds; keep prior snapshot. No silent catalog changes affecting a running job without a migration. If importing a prototype from the uncapped v1.0 candidate, preserve every existing item and reservation; derive new base/module cap (default base160 if no module migrated). If over, allow spending, explicit discard of ordinary stock and expansion while blocking net-increasing warehouse credits until back within capacity; do not truncate inventory. Persist per-resource policy and held batches, derive capacity rather than trust saved totals.

## Performance and diagnostics

Target on ordinary modern mobile browser: UI responds to input within 100ms perceived time, animation 60fps where possible, domain work does not monopolize UI. Offline 12h with all v1 slot caps and realistic running schedule must not hang: batch identical events where safe, move long calculation off-main-thread if necessary; show progress with last good state and a safe cancel/resume (not a duplicate reward). Initial target p95 <2s typical 12h mature-world replay, <10s stress cap on test devices; if exceeded optimize with measured traces before claiming release. Keep inventory summaries derived/cached, virtualize long lists, cap particle animations independent of simulation. Include local non-sensitive debug snapshot (version, task states, resource deltas, simulation duration, blocked reasons, error component) exportable only by player action. No external telemetry in baseline.
